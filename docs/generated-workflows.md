# Generate a free PR workflow

Build the source candidate containing `workflow`; published earlier runners still support their documented manual CI setup. The generator takes explicit choices and refuses an existing output file. Preview with `--print` before writing:

```sh
playtestr workflow --source-revision FULL_40_CHARACTER_CANDIDATE_SHA \
  --os linux --suite examples/recorded/fullscreen.json \
  --build 'go build -o bin/demo ./cmd/demo' --print
```

Omit `--print` to create `.github/workflows/playtestr.yml`, or choose `--output`. Repeat `--suite`, `--setup` and `--build`; prerequisite/build commands are explicit bash scripts that you review, even on Windows. No target installation is hidden in Playtestr's Action. Use `--os linux,macos,windows` only if those explicit build commands and targets work on all selected hosts. Standard `ubuntu-24.04`, `macos-15` and `windows-2025` runners are the admitted template choices. Workflow-level limits are 1–60 minutes, retention 1–30 days (default 14). A customer may edit its reviewed YAML deliberately.

Candidate mode checks out the exact Playtestr source SHA separately, builds that runner, and verifies `source-SHA`. Summary/context helpers come from that same SHA. Action identities are independently pinned to full commits. This is a source-build route requiring Go and Python, not an unpublished downloadable release. Alternatively choose `--runner-version vX.Y.Z[-suffix]` and `--tooling-revision FULL_SHA` for a real published exact runner and pinned helpers; the existing checksum-verifying setup Action is reused. Review that the selected released runner supports your spec. No release is published by this command.

The generated check triggers real `pull_request` events opened/synchronize/reopened/ready_for_review, plus manual dispatch for diagnosis. PR checkout uses GitHub's tested merge; `context.json` records the PR head, base and actual checked-out SHA distinctly, with run/attempt, runner binary hash, selected tests and bounded hashes of test, snapshot, fixture and available target binaries. No command arguments/environment values are placed in that metadata. The ordinary report records runner version, OS/architecture, outcomes and cleanup. These are customer-controlled CI records and can be tampered with inside that job; they are not malicious-admin-proof attestation. P3 adds review policy, not a replacement for this trust boundary.

Zero selection, invalid specs, missing snapshots/dependencies, identity mismatches or excessive inventories fail. Selection/context runs before tests; missing context prevents execution. The original test exit remains nonzero while `always()` steps render HTML, summarize and upload bounded runner evidence. Summaries include counts, exact revisions, failure categories, cleanup and artifact/run links. Setup/helper/report failures produce non-success and explain missing evidence. No automatic retry erases a regression. New PR updates cancel superseded runs; a hard cancellation can prevent all final steps, so absent evidence is unavailable rather than proof of a pass. Artifact upload success must be checked independently of local report generation.

Fork code runs only in ephemeral `pull_request` jobs, with `contents: read`, checkout credentials removed, no App/payment/service secrets and no `pull_request_target` or self-hosted host. A repository can require approval before a fork job executes. Approve only trusted test cases; execution uses Actions capacity independently of any Playtestr subscription. Public standard hosted runs and private quotas/overages have different [GitHub billing rules](https://docs.github.com/en/billing/concepts/product-billing/github-actions). Fork tests need no paid App or write-token comment bot.

Download the exact failed run's artifact before its retention expires. Check `context.json`, `results.json`, screen/diff files and `report.html`. Checkout the recorded **tested SHA**, install/build the pinned runner, run the committed workflow's explicit prerequisites/build and `playtestr test` with `selected_specs`. Compare contract/binary identities, not a newer branch. Target binaries can differ across native hosts even when source is identical; reproduce application behavior and document that platform distinction. A deliberate behavior change is maintained with one selected `test --update --snapshot ...`, reviewed in Git, committed and rerun; never auto-update baselines in CI.

Repository owners choose required checks manually in branch/ruleset settings using the stable generated job names `Playtestr tests (ubuntu-24.04)` etc. Require each admitted platform's check. This template has no merge-queue/`merge_group`, push-to-main enforcement, privileged postprocessor, paid review gate or reusable-workflow support; do not configure requirements for unsupported events. It runs on every selected PR, with no path filter that could leave a required check absent. A draft acceptance PR is still a real PR run.

Artifacts follow GitHub repository access and can contain target output, including secrets printed by an application. Retention can be shortened by repository policy; after expiry/deletion report context is unavailable. The template does not persist source or raw streams on a Playtestr service. Removal: remove required-check/ruleset references first, delete the generated workflow, remove optional setup/build tools, and delete recorded tests/fixtures/baselines only deliberately. There is no account, subscription, server or App to uninstall for the free workflow.
